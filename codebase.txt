# Project Architecture & System Overview: SlurdleTwo

## 1. Overview & System Purpose
SlurdleTwo is a Python-based web quiz application that tests users on demographic and ethnic slurs and their historical origins. It features an automated data scraping pipeline, semantic representation of demographic targets using SentenceTransformers on Apple Silicon Metal (MPS), a Flask MVC web server, and a Tailwind CSS v4 frontend.

## 2. Architecture & Pattern
- Core Pattern: Monolithic MVC (Model-View-Controller) supported by offline batch ETL and vector embedding pipelines.
- Pipelines:
  1. ETL Pipeline: Pulls HTML records from rsdb.org, normalizes target variations/typos, outputs to CSV and SQLite.
  2. Semantic Pipeline: Encodes distinct demographic targets into vector embeddings using Hugging Face models, computing an N x N cosine similarity matrix.
  3. Web Runtime: Serves randomized question sessions via Flask, validating user guesses asynchronously over JSON endpoints.

## 3. Directory Layout & Key Modules
- main.py: CLI entry point with flags:
  - --init: Scrapes and initializes the SQLite database.
  - --refresh: Cleans previous artifacts and re-initializes data.
  - --weights: Computes cosine similarity matrices via SentenceTransformers.
  - --run: Starts the Flask development server on port 5001.
- app.py: Flask application controller. Defines:
  - GET /: Generates random slur question and stores correct answer in session.
  - POST /guess: Validates user selection against session data and returns origin explanation.
- src/config.py: Filesystem path constants (ROOT_DIR, DATA_DIR, SLURS_DB, etc.).
- src/pull.py: Ingestion script fetching from rsdb.org/full using requests + BeautifulSoup, applying target corrections, and saving to data/slurs.html, data/slurs.csv, and data/slurs.db.
- src/slurs.py: Database query logic for sampling random slurs, generating negative distractor options via regex/string matching, and assembling question payloads.
- src/weights.py: Semantic embedding generator using models (bge-large-en-v1.5 and paraphrase-multilingual-mpnet-base-v2) on MPS to produce similarity weights.
- templates/base.jinja & templates/index.jinja: Frontend Jinja2 templates.
- static/app.js: Client-side event handler for clicks, asynchronous guess submissions, dialog modals, and shake feedback.
- static/src/input.css: Tailwind CSS v4 design system with custom color gradients, animations (glow, shake, bounce, gradientShift), and typography.

## 4. Data Flow
1. Scraping / ETL:
   rsdb.org -> src/pull.py -> data/slurs.html -> data/slurs.csv -> data/slurs.db (table 'slurs')
2. Semantic Weighting:
   data/slurs.db -> src/weights.py (SentenceTransformers / MPS) -> data/target_weights_*.csv
3. Quiz Gameplay:
   Browser GET / -> app.py -> src/slurs.py (queries slurs.db) -> Session cookie -> templates/index.jinja -> Browser DOM.
   User Click -> static/app.js -> POST /guess -> app.py checks session -> JSON response -> modal display.

## 5. Key Dependencies
- Python: Flask, pandas, beautifulsoup4, requests, sentence-transformers, scikit-learn, lxml.
- Node / Tooling: Yarn v4, @tailwindcss/cli, Tailwind CSS v4.
- Acceleration: Apple Silicon Metal (MPS) for PyTorch / SentenceTransformers.
- Database: Embedded SQLite3 (data/slurs.db).

## 6. Current Architectural Observations & Next Steps
- The similarity matrices generated in src/weights.py are currently stored offline and not yet linked to live gameplay in src/slurs.py.
- Secret key in app.py is hardcoded ("your-secret-key") and should be externalized.
- Database queries in src/slurs.py format strings directly; converting to parameterized queries will ensure robustness.
